## 2. 三个功能

### 2.1 慢动作时段上限：3 分钟 → 25 分钟

| 项 | 值 |
|---|---|
| 位置 | `0x102A0470`（模块偏移 `0x280470`） |
| 改动 | 4 字节：`180000` → `1500000` ms |
| 实测 | 已录 **10 分钟**正常（远超原厂 3 分钟）；**25 分钟满程未验证** |

### 2.2 视频码率提升（1080p）

表在 `0x10717144`，30 条 × `0x1C`，字段 `+0x14` 最大 / `+0x18` 平均：

| 记录 | 模式 | 原厂 | 现在 |
|---|---|---|---|
| 6 / 8 | 1080p 60 / 50 高品质 | 56/48 | **84/70** |
| 7 / 9 | 1080p 60 / 50 标准 | 28/24 | **56/48** |
| 10 / 12 / 14 | 1080p 30 / 25 / 24 高品质 | 28/24 | **56/48** |
| 11 / 13 / 15 | 1080p 30 / 25 / 24 标准 | 14/12 | **28/24** |
| 0–5 | 4K 24 / 25 / 30 | 144/120、72/60 | **未动**（用户判定已够） |

**实测（MediaInfo Data rate）**：

| 格式 | 档位 | 目标 max/avg | 实测 | 判读 |
|---|---|---|---|---|
| 1080p 59.94 | 标准 | 56/48 | **50.8** | +5.8% ✓ |
| 1080p 50.00 | 标准 | 56/48 | **48.3** | +0.6% ✓ |
| 1080p 29.97 | 标准 | 28/24 | **25.5** | +6.4% ✓ |
| 1080p 25.00 | 标准 | 28/24 | **23.6** | −1.5% ✓ |
| 1080p 23.98 | 标准 | 28/24 | **24.2** | +0.8% ✓ |
| 1080p 59.94 | 高品质 | 84/70 | **70.2** | +0.4% ✓ |
| 1080p 29.97 | 高品质 | 56/48 | **44.8** | −6.6% ✓ |
| **4K 29.97** | 高品质 | 144/120（未改） | **131.0** | 对照组 ✓ |

4K 对照组的意义：原厂 4K 就在跑 131 Mbps → 卡速与编码器通路能扛 131 Mbps，
1080p 的 84 Mbps 对硬件是小菜。

### 2.3 照片取景斑马纹

| 项 | 值 |
|---|---|
| 位置 | `0x101765DE` / `0x1017670A`（模块偏移 `0x1565DE` / `0x15670A`） |
| 改动 | 4 字节：`cbz r5,reject`（`9db1`）→ `nop`（`00bf`），2 处 |
| 实测 | 照片取景出现条纹；**用原厂视频菜单的「加亮显示」可正常开关**；不需要独立菜单、不需要代码注入 |

机制：这两处是"高光显示资格回调"，门里有三个否决点，实测只有第一个
（`r6` 的 bit 5/7/9）在拦照片模式，另外两个（状态码 `!= 3`、分类器 `!= 0`）本来就通过。

## 4. 明确的边界（别再重复）

| 方向 | 结论 |
|---|---|
| 普通录像 30 分钟 | **结案**：限制方不读时长表，改表/改可见代码都碰不到（三轮实机 + 全量静态分析） |
| `video10m` 绕过实验 | **作废**：逻辑上绕不出去（即使 10:00 停，要变长仍得让表 >1799000，引擎启动即拒） |
| **720p** | **本机型没有这个模式**。表里 `rec20–23` 确实编码成 1280×720，但 Z fc 菜单不提供 → 死路径，改它等于改没人读的数据 |
| 4K / 1080p100/120 的「标准」档 | 掩码 `1`（只有高品质）。改成 `3` 后菜单**能出现**标准项，但仍不可选 —— 第二道门（设置项可设置性）在 UI 子系统。收益是**更低**码率，暂不做 |
| 4K 码率再提高 | 用户判定 4K 144/120 已够，不再提 |
| 代码注入 | 目前**没有任何功能需要它**（斑马纹靠 2 字节 × 2 处就够了） |

## 6. 第二档：代码注入能力（已跑通）

原计划是"先做 video-rot"，实际顺序变成了"先把注入能力打通，再试 video-rot"。

### 6.1 关键问题的答案

| 问题 | 结论 |
|---|---|
| 安装器接受更大的模块吗？ | **接受**。`grow-probe`（原厂 + 64 字节 0x00 + 重算 CRC）装进去一切正常 |
| 代码段里有函数间填充可停放代码吗？ | **没有**。76 个 ≥64 字节零区，0 个两侧是函数边界 |
| 尾部 12.4 KB 零区能用吗？ | **不能**。26 个指针指向它（11 个在代码段、7 个在高熵区） |
| 追加区可执行吗？ | **可执行**。`inject-smoke` 把斑马纹改成经注入实现，表现与 2 字节 nop 版完全一致 |

### 6.2 交付的工具

`tools/build_inject.py` —— 与 `patch.py` 同级的第二类构建模式：

- 追加 Thumb 代码块（keystone 汇编）与数据块（原样 hex）
- 支持 `{{name_lo}}` / `{{name_hi}}` 占位符跨块引用地址
- 站点窗口用 `ldr.w pc,[pc,#imm]` + 字面量 + NOP 填充（8/10 字节均可）
- 闸门：`expected` 逐字节校验、**原始区间只允许声明窗口变化**、追加 ≤1 MB、CRC 残差 0
- 成品用 capstone 回读并写进报告

### 6.3 踩到并解决的坑（重要）

**ARM / Thumb 状态**：`0x10198A48` 是 **ARM 的 memcpy**（原厂用 `blx <imm>` 调用，该形式强制切 ARM）。
第一次移植时用了 `addr|1`（置 Thumb 位）→ 用 Thumb 解释 ARM 字节 → 停止录像时硬 fault、看门狗重启、文件没写完。

规则：**目标函数是 ARM 时用 `addr & ~1` + `blx`；是 Thumb 时用 `addr | 1` + `blx`。**
判据：原厂用 `blx <imm>` 调的就是 ARM。

### 6.4 video-rot：未完成，已挂起

已确认的正面结果：

- 写 tkhd 的位置找到了：`0x102EC628` 把矩阵拷到栈，再 `memcpy(ctx+0x91, 36)`（上下文里的矩阵槽）
- D2 证明**我们能任意指定方向并写进文件**（强制 90° 后横拍视频确实被标成 90°）

卡住的地方 —— **找不到可用的"实时姿态"数据源**：

| 候选 | 为什么不行 |
|---|---|
| 方向获取函数 `0x10218AD6` | 读实时方向的分支要求 `[0xC1807DDC+0xc] == 1`，配置/写头时**恒不成立** |
| 它读的字节 `0xC1D41FA8` | **全镜像无写入者**（基址 `0xC1D41EA8` 也只被 getter 自己引用）→ RAM 初始化常量 3 |
| EXIF 方向表 `{1,6,8,3}` @ `0x1178DF40` | 表存在（pose→EXIF 1/6/8/3），但**无任何 u32 指向**，只能经基址+偏移访问，基址疑似在高熵区 |

补充事实：**Z30 项目自己也没在机身验证过 video-rot**（其 `video_rot.py` 写着
`camera_verified: False, pose_direction_device_verified: False`），这条线我们是第一个走到这里的。

**若以后要继续**：最有希望的入口是找 EXIF 方向标签 `0x0112` 的写入代码 ——
照片 EXIF 方向是正常工作的，那条路径一定握着可用姿态值。
