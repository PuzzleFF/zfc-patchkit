# 视频模式表 + 索引映射器：完整结构（2026-10-25）

> 目标：搞清 `0x10717144` 那张 30 条记录的表到底怎么被索引，
> 从而回答"1080p100/120 为什么没有 normal 画质、能不能解锁"。
> 工具：`tools/inspect_mode_table.py`、`tools/find_mode_table_user.py`

---

## 1. 记录的字段布局（已解出）

每条 `0x1C` 字节，7 个 word：

| 偏移 | 含义 | 例（rec6 = 1080/59.94 高） |
|---|---|---|
| `+0x00` | `(高度<<16) \| 宽度` | `04380780` = 1080 / 1920 |
| `+0x04` | 帧率分子（×1000） | `0000EA60` = 60000 |
| `+0x08` | 帧率分母 | `000003E9` = 1001 → 59.94 |
| `+0x0C` | 恒 0 | — |
| `+0x10` | **高半字** = 与帧率相关（见 §4）；**低半字** = **1 或 3**（画质可用性，见 §4） | `001E0003` → 30 / 3 |
| `+0x14` | 最大码率 (bps) | `03567E00` = 56,000,000 |
| `+0x18` | 平均码率 (bps) | `02DC6C00` = 48,000,000 |

于是 30 条全部可读，不需要实机反推。

## 2. 索引映射器 `0x103543DC`

签名是 `void map(uint8_t in[3], uint8_t *out)`：

- `in[0]` = **组**（0 = 4K、1 = 1080、2 = 720p）
- `in[1]` = **组内类别**（帧率/变体）
- `in[2]` = **画质选择位**：`0` → 偶数索引（高档），`非 0` → 奇数索引（normal 档）

记录地址由两个薄封装算出（`0x103544C4` 整条拷贝 / `0x103544E6` 只取一个 u16）：

```
r0 = 索引
r0 = r0*8 - r0            ; = 7*index
r1 = r0 << 2              ; = index*0x1C
addr = 0x10717144 + r1    ; 就是 &table[index]
```

完整映射（`偶数/奇数` = 高档 / normal）：

| 组 | 类别 `in[1]` | 分辨率 | 帧率 | 记录 | 档位值（max/avg Mbps） |
|---|---|---|---|---|---|
| 0 | 2 | 3840×2160 | 29.97 | 0/1 | 144/120、72/60 |
| 0 | 3 | 3840×2160 | 25.00 | 2/3 | 144/120、72/60 |
| 0 | 4 | 3840×2160 | 23.98 | 4/5 | 144/120、72/60 |
| 1 | 0 | 1920×1080 | 59.94 | 6/7 | 56/48、28/24 |
| 1 | 1 | 1920×1080 | 50.00 | 8/9 | 56/48、28/24 |
| 1 | 2 | 1920×1080 | 29.97 | 10/11 | 28/24、14/12 |
| 1 | 3 | 1920×1080 | 25.00 | 12/13 | 28/24、14/12 |
| 1 | 4 | 1920×1080 | 23.98 | 14/15 | 28/24、14/12 |
| 1 | 5 | 1920×1080 | **119.88** | **16/17** | **144/120、72/60** |
| 1 | 6 | 1920×1080 | **100.00** | **18/19** | **144/120、72/60** |
| 1 | 7 | 1920×1080 | 119.88 | 24/25 | 144/120、72/60 |
| 1 | 8 | 1920×1080 | 100.00 | 26/27 | 144/120、72/60 |
| 1 | 9 | 1920×1080 | 119.88 | 28/29 | 144/120、72/60 |
| 2 | 0 | 1280×720 | 59.94 | 20/21 | 28/24、14/12 |
| 2 | 1 | 1280×720 | 50.00 | 22/23 | 28/24、14/12 |

> **⚠ 可达性警告（2026-10-25 更正）**：Z fc 的规格**只有 4K 和 1080p，没有 1280×720**。
> 也就是说组 2（`rec20–23`）在本机型上是**死路径** —— 表里条目的分辨率字段虽然精确编码成
> 1280/720，但菜单不会提供这个模式，改它的码率等于改一段没人读的数据。
> **教训：表里有条目 ≠ 本机型支持该模式。** 这张表是跨机型共用的，
> 任何"优化某条记录"的想法都要先确认该模式在 Z fc 上真的可选。

**三条重要推论：**

1. **每一种模式在表里都有"normal"条目** —— 映射器的 `in[2]` 分支永远存在
   （`cbz r0` → 偶数，否则奇数）。所以 1080p100/120 没有 normal **不是表缺数据**，
   而是别处不让选。这和斑马纹的结论同类。
2. **rec24–29 是慢动作的三个变体**：它们与前两条重复了 119.88/100 的分辨率帧率，
   区别在 `+0x10` 高半字（60 / 12 / 12）→ 对应**输出帧率 30p / 25p / 24p**：
   - 类别 7 → rec24/25 = 1080/119.88 → 30p 输出 = **慢动作 4x**
   - 类别 8 → rec26/27 = 1080/100 → 25p 输出 = **慢动作 4x（PAL）**
   - 类别 9 → rec28/29 = 1080/119.88 → 24p 输出 = **慢动作 5x**
   → **慢动作的码率是独立的一组记录**（当前 144/120 与 72/60，已经不低）
3. 720p 也存在，当前只有 28/24 与 14/12，是表里最低的。

## 3. 关键假设：`+0x10` 低半字 = **画质可用性掩码**

全表只有两个取值：

| 低半字 | 记录 | 观察 |
|---|---|---|
| `3` | rec6–15（1080 30–60fps）、rec20–23（720p） | 这些模式**都有**「高品质 / 标准」两项 |
| `1` | rec0–5（4K）、rec16–19（1080 100/120）、rec24–29（慢动作） | 实测 1080 100p 以上**只有高品质** ✓ |

`3` = 二进制 `11` = 两档都可用；`1` = `01` = 只有一档 —— 语义吻合。
已知实测证据支持 1080 档位；**4K 是唯一还没核对的预测：如果 4K 也只有「高品质」，
这个假设就成立**。

## 3b. 实测结果（2026-10-25）：掩码只管"选项出现"，不管"能不能选"

把 `rec16/17` 的 `+0x10` 低字节 `1 → 3` 后刷入实测：

| | 之前 | 之后 |
|---|---|---|
| 1080p119.88 菜单里的 norm 选项 | 灰色，**不能移过去** | **能移过去**（说明选项确实出现了）✓ |
| 能不能真的切到 norm | 不能 | **仍然不能**（norm 与 high 两个都是灰的） |
| 实际录制 | high（码率 125 Mbps） | **仍然 high**（125 Mbps，见 ZFC_3092） |

→ **假设前半段成立**：`+0x10` 低字节确实是"这一行列几个画质档"的掩码。
→ **还有第二道门**：整行被禁用（`quality` 的**可设置性**），掩码管不到它。

## 3c. 谁读了掩码：访问链已定位

| 地址 | 作用 |
|---|---|
| `0x103543DC` | `map(in[0..2] → index)`：组 / 类别 / 画质位 → 记录索引 |
| `0x103544C4` | 把 0x1C 字节记录整体拷给调用者（6 个调用者，5 个在 `0x102A96xx`–`0x102ABxxx` = 容量/剩余时间计算，1 个在 `0x104EE494`） |
| `0x103544E6` | 只读 `record+0x12` 的 u16（帧率码），唯一调用者 `0x102A9800` |
| `0x104EE468` | **取值器**：`*out1 = record[0x10]`（掩码）、`*out2 = record[0x12]`（帧率码） |
| `0x104E55D8` | `0x104EE468` 的**唯一**调用者：把帧率码当**除数**做时间换算，**没有使用掩码**（`sp+4` 那个输出是死值） |

也就是说：**掩码在这个函数链里没有人拿来做"可设置性"判断**。
菜单那边的禁用状态由别的子系统决定（很可能是设置项的"本模式是否可改"属性表），
不在模式表里，也不在这几个访问器里。

## 3d. 掩码语义：**已完全确认**（2026-10-25 实测四组全对）

| 掩码 | 记录 | 菜单实测（用户逐项确认） |
|---|---|---|
| `3`（`11`） | rec6–15（1080 30/25/24/50/60p）、rec20–23（720p 60/50p） | **高品质 + 标准** ✓ |
| `1`（`01`） | rec0–5（4K 24/25/30p）、rec16–19（1080 100/120p）、rec24–29（慢动作） | **只有高品质** ✓ |

→ **`+0x10` 低字节 = 该模式可用的画质档位掩码**，bit0 = 高品质，bit1 = 标准。

**重要更正**：既然 4K 只有高品质，`rec1/3/5` 里的 `72/60` 就是**从未启用的 normal 槽位**
（与 120p 的 `rec17/19` 同性质）。所以"把 4K 标准档提到 144/120"这个建议**作废** ——
没有标准档可提。4K 唯一能动的画质旋钮是把**高品质**的 144/120 再往上推（收益边际递减）。

## 3e. 为什么改了掩码还是选不了

改 `rec16/17` 掩码 `1 → 3` 后的实测：

| | 之前 | 之后 |
|---|---|---|
| norm 选项 | 灰色、**不能移过去** | **能移过去**（选项确实出现了）✓ |
| 实际切到 norm | 不能 | **仍然不能**（仍录 high，125 Mbps） |
| 菜单表现 | — | 两个选框都是灰的 |

→ 掩码决定"**这一行列几个档位**"，但不决定"**能不能设置**"。
第二道门（设置项在本模式是否可改）在设置/UI 子系统，**不在模式表、也不在下面这几个访问器里**（见 §3c）。

## 3f. 是否值得继续

- 收益**偏低**：解锁出来的是**更低码率**的档位（72/60 vs 144/120），
  换来更小文件/更长录制；对画质是降低，不是提升
- 成本**不确定**：第二道门要在设置子系统里找，可能几小时到几天，改动面比现有补丁都大
- 建议：**不在正式镜像里带这个实验**（把 `rec16/17` 掩码改回 `1`），
  真要攻就单开一条线，且先确认"低码率 120p/4K"对你有多少价值

## 4. 假设成立时的解锁方式（保留备查）

对要解锁的记录，把 `+0x10` 的低半字 `1` 改成 `3`：

```
rec16/17 (1080/119.88)  +0x10: 003C0001 -> 003C0003
rec18/19 (1080/100)     +0x10: 00300001 -> 00300003
```

改动后映射器本来就会返回 `index+1`（72/60 Mbps 的 normal 档），
**不需要发明任何码率值，也不改代码**。

建议**先只改 rec16/17**（120p），一次刷机验证菜单是否出现「标准」、
选中后实测码率是否落到 72/60；成功再补 100p。

## 5. 还没解决的

- `+0x10` 高半字的精确含义（与帧率相关，但 50/100 两个档位比 "fps/2" 少 1，
  规律不明）。**不影响本次解锁**，因为只改低半字
- 谁决定 `in[2]`（画质选择位）能取什么值 —— 如果改低半字不够，
  下一步就是从 `0x103544C4` / `0x103544E6` 的调用者往上追
