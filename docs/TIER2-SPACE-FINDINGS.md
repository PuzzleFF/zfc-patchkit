# 第二档侦察：代码停放空间与 video-rot（2026-10-25）

## 1. 第一档结论

### 1.1 video-rot（视频方向元数据）→ 归入第二档

Z30 的实现（`video_rot.py`）不是小补丁，它需要：

- 2 个 hook（mux 配置 + 写 tkhd 时）
- 3 段注入代码（配置包装约 192 B + 拷贝包装约 64 B + 4×36 B 矩阵表）
- 一个方向获取调用

Z fc 的三处锚点**全部存在**：

| 锚点 | Z30 | Z fc | 说明 |
|---|---|---|---|
| tkhd 单位矩阵（36 B） | `0x102EDE28` | **`0x102EB50C`** | Z fc 同样只有"永不旋转"的常量 |
| 方向获取函数前缀 | `0x1021B5F6` | **`0x10218AD6`** | 方向 API 存在 |
| mux 配置函数前缀 | `0x102EF402` | **`0x102ECAE2`** | 配置点存在 |
| 写 tkhd 时的拷贝点 | `0x102EE81E` | **未命中** | 指令序列不同，需另找 |

三处位移分别是 `-0x291C`、`-0x2B20`、`-0x2920` —— **又不是常数**，逐函数定址。

→ **结论：这是个约 200 字节的注入移植，必须等第二档（空间 + 注入工具）就绪。**

### 1.2 JPEG 量化表 → 暂缓（收益低）

- Z fc 用的是**标准 Annex K 表**：亮度 `0x115EAC70`、色度 `0x115EACB0`（两块相邻，`+0x40`）
- 亮度表只被一个文字池引用（`0x1012D980`，池内还有 `0x115EA59C`、`0x115EA9F8`）
- `0x1012D962` 是个**质量缩放函数**：`scale = f(quality_table, 50) * x >> 8`，带下限钳制
- 表前 `0x115EAC20..0x115EAC6C` 是一串 u32（85/123/87/120…/150/68），很像质量系数

→ 要继续就得把"菜单的优/标准 → 缩放索引"这段解开（还需 1–2 小时），
而收益是"细节略好、文件更大"，**优先级低**。等真没别的可做时再回来。

## 2. 第二档前置：代码停放空间

### 2.1 代码段内没有函数间填充

`tools/find_padding_caves.py` 的判据比"没有指针指向"严格得多：

- 洞前 16 字节内必须有函数收尾（`bx lr` 0x4770 / `pop {..,pc}` 0xBDxx / `pop.w` 0xE8BD）
- 洞后 8 字节内必须有函数开头（`push` 0xB4xx/0xB5xx / `push.w` 0xE92D）
- 无 u32 指向、无 16 位分支落入

结果：代码段 76 个 ≥64 字节零区，**符合条件 0 个** —— 编译器把函数排得很紧，没有空隙。

### 2.2 唯一"无引用"的空区在数据区，可执行性未知

`0x105E3D38..0x105E412C`（1,012 字节）无 u32 指向；
`tools/check_code_cave.py` 扫出唯一的"分支落入"是 `0x103DBA6A` 的 `bl`，
但核对指令流后是**误判**（`0x103DBA68` 的 4 字节 `mul` 覆盖了那个偏移）。

不过它两侧是**数据**（不是函数边界），所以"能执行"没有保证 —— 要有 MMU 属性或实测才能定。

### 2.3 安装器的尺寸校验（静态读不出方向）

`FUN_101cbf24` 的头几行：

```
r0 = [ctx + 0x218]
r1 = [0xC2594C90 + 0x10]      ; DAT_101cc324 里存的是 RAM 指针 0xC2594C90
if (r1 >= r0) ok else return 0x0B
```

方向是"其中一个必须 ≥ 另一个"，但 `0xC2594C90+0x10` 是运行时写入的字段，
静态无法判定谁是"文件实际大小"。

### 2.4 因此做一个一次性探针：`build/sd/grow-probe/`

**原厂模块 + 末尾追加 64 字节 0x00 + 重算 CRC**，其余每个字节都不变：

```
stock 35,021,690  ->  probe 35,021,754  (+64)
payload byte-identical: True     appended: 64 zero bytes     crc residue 0x0000
```

- 相机**接受** → 允许长大 → 第二档解锁（Z30 用了约 9 MB 余量）
- 相机**拒绝** → 第二档改走"数据区空区 + 可执行性验证"，成本更高

## 4. 第一次注入移植：踩到的坑（必须记住）

### 4.1 现象

`inject-rot` 第一版刷入后：**停止录像时死机、自动重启、SD 卡没有文件**（两次复现）。

### 4.2 根因：ARM / Thumb 状态搞错

原厂那条指令是：

```
0x102EC638  acf606ea   blx #0x10198a48
```

**`blx <imm>` 在 Thumb 里永远是"切换到 ARM 状态"的调用** —— 也就是说
`0x10198A48` 是 **ARM 代码**（`push {r4,lr}` + `ldm/stm` 拷贝循环，ARM 解码完全合理；
用 Thumb 解码只有 `ands r0,r2` 这种垃圾）。

我写注入代码时用了 `movw r12, #0x8a49`（**置了 Thumb 位**），`blx r12` 于是留在 Thumb
状态去执行 ARM 字节 → 立刻 fault → 看门狗重启 → 文件没写完。

Z30 项目里对应写法是 `invoke(MEMCPY, thumb=False)`，正是这个原因，我漏看了。

### 4.3 规则（写进工具注释与本文）

- 目标函数是 **Thumb** → `movw/movt r12, addr|1` + `blx r12`
- 目标函数是 **ARM** → `movw/movt r12, addr&~1` + `blx r12`
- 判断依据：原厂代码若用 `blx <imm>` 调用它，就是 ARM；若用 `bl`/`blx rN` 且地址为奇数，
  就是 Thumb。**移植前必须先确认状态**，否则必定死机

### 4.4 诊断镜像 D1

`build/sd/inject-rot-d1/`：同样的 hook，但**不调用方向获取函数**，只把
`0x102EB50C` 那张原厂矩阵按原样拷一遍 —— 行为应与原厂**完全一致**（纯搬迁）。

用途：把"hook 机制 + ARM 调用"与"方向获取函数是否可在此任务上下文调用"分开。
- D1 正常 → 机制没问题，再刷 `inject-rot` 看 getter 是否安全
- D1 仍死机 → 机制还有问题

### 4.5 仍需验证的疑点

方向获取函数 `0x10218AD6` 在 mux 任务上下文里**是否可调用**还没证实：
它读的是 `[0x10218AD6+pool]` 指向的全局结构（很可能是状态管理器的，属于别的任务）。
若 D1 通过而 `inject-rot` 死机，就说明这个 getter 不能在这里调，
应改回 Z30 的"在 mux 配置时锁存方向"方案（需要第二个 hook：Z30 是 `0x102EF402`，
Z fc 对应 `0x102ECAE2`）。
