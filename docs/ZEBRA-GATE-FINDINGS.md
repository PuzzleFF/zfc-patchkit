# 斑马纹（高光显示）在 Z fc 上的定位结果

> 2026-10-25。目的：判断 `NEXT-IDEAS.md` 2.1「照片取景斑马纹」要多少工作量。
> 复现脚本：`tools/scan_zebra.py`、`tools/cmp_zebra.py`、`tools/disasm_zebra.py`、
> `tools/disasm_zebra_ctx.py`、`tools/trace_zebra_cb.py`
> 依赖：capstone（`tools/fetch_emu_wheels.py` 装到 `.pylibs`）

**✅ 2026-10-25 实机验证通过（A 版）**：刷入 `build/sd/zebra-photo/` 后，
照片取景出现斑马纹，并且**用原厂视频菜单的「加亮显示」可以正常开关**。
→ 三个否决点里只有 **#1（`cbz r5`，`r6` 的 bit 5/7/9）** 在拦照片模式；
#2（状态码 `!= 3`）和 #3（分类器 `!= 0`）在照片模式下本来就通过。
→ **不需要独立开关，也不需要代码注入**：原厂设置项直接复用，
`zebra-photo-all` 只是诊断镜像，不必再用。

**一句话结论**：两道门的位置 100% 确定，**改动就是 `gate+4` 那 2 个字节 × 2 处**
（`9db1` → `00bf`），且已在机身验证。

## 1. 直接命中（已确认）

把 Z30 那 12 字节门的后 8 字节在 Z fc 的 `eg1985_018100.bi` 里搜，**各命中 1 处**：

| 门 | Z fc 地址 | 窗口字节 |
|---|---|---|
| A 生效图案（effective pattern） | **`0x101765DA`** | `ecf72afe 9db1 032c 11d1 06e0` |
| B 可用性（availability） | **`0x10176706`** | `ecf794fd 9db1 032f 11d1 06e0` |

Z30（`0x101777F2` / `0x1017791E`）与 Z fc **逐字节只差 BL 位移**；
两道门都给出同一个位移 `Z fc = Z30 − 0x1218`，窗口后 64 字节有 62–63 字节相同。

**第一个实质差别**：Z30 的门 `bl 0x10164526`，Z fc 的门 `bl 0x10163232`。
`0x10163232 + 0x1218 = 0x1016444A ≠ 0x10164526`（差 `0xDC`）。
→ **位移不是全局常数**，每个被调函数要单独定址。
所以"拿 Z30 的注入代码 + 一个位移搬过来"这条路**不成立**，
必须逐个解析它内嵌的绝对地址。

## 2. 窗口语义（capstone 实测）

```
0x101765DA  ecf72afe  bl  0x10163232       ; 取某个状态
0x101765DE  9db1      cbz r5, 0x10176608   ; r5 == 0 -> 拒绝
0x101765E0  032c      cmp r4, #3
0x101765E2  11d1      bne 0x10176608       ; r4 != 3 -> 拒绝
0x101765E4  06e0      b 0x101765f4         ; 否则进入"原生资格链"
```

- **accept = `0x101765F4`**（= gate+0x1A），**reject = `0x10176608`**（= gate+0x2E）
  与 Z30 文档的 accept/reject 偏移完全一致，说明两边是同一份源码
- 但 `0x101765F4` **不是"放行"**，它是**一串原生资格检查的开头**：
  ```c
  if (r0 != 0) reject;                 // r0 = 上面那次 bl 的返回值
  if (r6 & (1<<13)) reject;
  if (r6 & (1<<14)) reject;
  if (r6 & (1<<16)) reject;
  if (sb != 0) reject;
  ```
  reject 的动作是 `movs r0,#0; str r0,[sp,#0x3c]`，然后汇合到 `0x1017660C`。
- 门 B 同构，只是比较的是 `r7`，reject = `0x10176734`，accept = `0x10176720`。

**门 A 所在回调的身份确认**：函数从 `0x101764E6` 开始（表项 `0x101764E7`），
开头就有 `movw r0, #0x189a` —— 正是"生效图案"属性 `0x189a`。

## 3. 为什么"2 字节改跳转"作废

上一版草稿提议把 `9db1`（`cbz r5`）或 `11d1`（`bne`）改成 `b accept`。**不行**，因为：

1. `r5` 不是"模式"。它的来源是函数中段的
   `0x10176532  mov r5, r0`（`r0` = `bl 0x101632b8` 的返回值）。
   同一个函数里 `0x10176536 cbz r5, ...` 已经把 `r5==0` 分流到另一条路，
   但 `cmp.w sl, #1` 的分支（`0x10176534 beq 0x101765e6`）会**绕过那个分流、
   直接汇合回主链**，所以门上的 `cbz r5` 仍是活的 —— 两条路都能到这里，`r5` 都有意义。
2. 真正的判别是 `r4 == 3`（门 B 是 `r7 == 3`），而 `r4` = `bl 0x1016ecec` 的返回值。
   把比较改掉等于**把两个输入都短路**，会连带跳过原生资格链里那 5 项检查。
3. Z30 的注入代码也不是"搬运"，它是**重新实现**：它自己测 `r6 & 0x2a1`（bit 0/5/7/9），
   而原生链测的是 `r6` 的 bit 13/14/16 —— **两组位完全不同**。
   说明 Z30 那套判据是**实机试出来的**，不是从原生代码读出来的。

## 4. 还缺什么（这才是下一步）

要定"改哪儿"，必须先知道这三个函数的语义（都在 `0x1016xxxx` / `0x1017xxxx`）：

| 函数 | 在哪被用 | 需要回答 |
|---|---|---|
| `0x101632b8` | `0x1017652A`，结果 → `r5` | 返回的 0/非 0 表示什么（设置是否开启？） |
| `0x1016ecec` | `0x101765D0`，结果 → `r4` | 为什么必须 `== 3`（图案编号？枚举"启用"？） |
| `0x1017cc84` | `0x10176510`/`0x10176650`，结果 → `sl`/`fp` | `== 1` 时走另一条喂参路径，这个 1 是什么 |

另外，**回调绑定记录**在 `0x115FDAEC` 一带（u32 视图）：

```
0x115FDAEC  0x00001099        0x115FDAF0  0x00000000
0x115FDAF4  0x115F5410        0x115FDAF8  0x115FAC7C
0x115FDAFC  0x101764E7  <cb A> 0x115FDB00  0x10176633  <cb B>
0x115FDB04  0x40000324        0x115FDB08  0x00000000
0x115FDB0C  0x115F555C        0x115FDB10  0x00000000
0x115FDB14  0x10176C25  <cb>  0x115FDB18  0x00000000
```

- 全镜像**没有任何 u32 指向这块记录**（0 处）→ 分发用"区基址 + 偏移"寻址
  （与 STATE 里"资源目录 `0x10F92AF8 → 0x12080000`"同一机制），
  所以逐指针查引用永远是 0，要找调用方得先确定它属于哪个区
- `0x40000324` / `0x1099` / `0x1414` 这几个字**很像"可用模式位掩码"**。
  如果照片模式被限制在**元数据**里，那这会是**纯数据补丁**（比改代码好得多）

## 5. 实机诊断结果：确认走代码，不走数据

**实测（2026-10-25）**：照片菜单里**没有**这一项；视频菜单里叫 **「加亮显示」**。

Z30 的文档给出的正是同样的事实，并且说明了他们的应对方式
（`build/wlz30/.../docs/photo-zebra.md`）：

> "`photo-zebra` 将原厂视频高光显示扩展到照片取景，复用原厂图案和八档阈值。"
> 使用步骤 2：**"在原厂高光显示设置中选择非关闭图案"**（也就是在**视频菜单**里设）
> "修改仅涉及**原厂高光资格回调**和独立菜单设置；阈值换算、显示请求构造、
> 照片图像数据路径和文件写入函数保持原厂实现。"

→ **照片侧本来就没有设置项，这是原厂菜单结构决定的**，不是缺一个数据开关。
门槛确实在我们找到的那两个回调里。所以上一版"数据 vs 代码"的二选一，答案是**代码**。

**菜单名更正**：固件里 `加亮顯示` 13 处、`高光顯示`（含 `高光顯示閾值`）3 处，是**两个不同文案**。
用户在视频菜单看到的是 `加亮显示`，那才是斑马纹项；`高光显示` 是另一处（很可能是回放的亮部警告）。

## 6. 代码停放空间：尾区**不可用**（上一版的乐观结论作废）

`0x121831E0 .. 0x12186376` 这 12,694 字节确实全是 0x00，但**并不空闲**。
`tools/check_free_tail.py` 把全镜像里指向该区间的 u32 全列了出来：

- **26 个指针**，散落在整个区间，最高到 `0x12186144`
- 按引用点所在区段分：**代码段 11 个**、资源/表区 8 个、高熵区 7 个
- 目标地址都是奇数偏移（`0x1218370E`、`0x12183B29`…）→ 像"一堆空字符串槽位"

结论：**在这段里写代码会覆盖被引用的空槽**，最坏情况是高熵区里那 7 个引用方
（不可读）出问题。掐掉最后一个目标后只剩 **554 字节**，还紧贴数据，不能用。

**替代方案：代码段内部的空洞。** `tools/find_code_caves.py` 扫"零字节 ≥96 且
没有任何 u32 指向"的区间，在代码段找到 46 处，最大一处：

```
0x105E3D38 .. 0x105E412C   1,012 字节，4 字节对齐
```

资源/表区另有一批 763 / 1,535 字节的空洞（合计约 26 KB）。但要注意：

- "没有 u32 指向" ≠ "安全" —— 表区可能用 `基址 + 序号×步长` 寻址（本项目已见过这种机制），
  按步长重复出现的 763 字节空洞尤其可疑
- 选定之前要确认它在函数边界之间（不是函数体内），以及附近没有 fall-through

→ 代码注入仍然可行，但需要**对一个候选空洞做 1 小时验证**，不是"12 KB 随手可用"。

## 6b. 三个否决点（`tools/disasm_zebra_helpers.py`）

门的完整语义现在读通了。`bl 0x10163232` 是个 **`tbb` 跳表分类器**
（输入 `fp & 0xff`、范围 0..0x22，返回 0 / 3 / 4），四个 helper 的身份：

| 函数 | 作用 | 结论 |
|---|---|---|
| `0x1017CC84` | `lsls r0,r0,#0x1f` + `movs r0,#0/1` | **`return x & 1`**（一个布尔位） |
| `0x101632B8` | `tst r5,#0xa0` + `lsls r1,r5,#0x16` 后 `bpl` | 当 `r6 & 0xA0`（bit 5/7）**或** `r6 & 0x200`（bit 9）时**提前返回 0** → 这就是 `r5 == 0` 的来源 |
| `0x1016ECEC` | 多处条件命中就 `movs r4,#3`，否则返回入参 | 返回"状态码"，**`== 3` 是某个枚举命中**，不是简单的模式布尔 |
| `0x10163232` | `cmp r1,#0x23` + `tbb [pc,r1]` | 0..0x22 的**查表分类器**，返回 0/3/4 |

**与 Z30 的吻合**：`0x101632B8` 测的是 bit 5/7/9，`0x1017CC84` 测的是 bit 0 ——
而 Z30 注入代码测的是 **`r6 & 0x2a1`（bit 0/5/7/9）**。
→ Z30 那个"经验值"其实正是原生这几条前置检查的压缩形式，**不是玄学**。
这反过来验证了我们对 `r6` 的读法是对的。

于是门内一共有**三个否决点**：

| # | 位置 | 指令 | 含义 |
|---|---|---|---|
| 1 | gate+4 | `cbz r5, reject` | `r6` 的 bit 5/7/9 任一置位就拒 |
| 2 | gate+8 | `bne reject`（`cmp r4,#3` 之后） | 状态码 `0x1016ECEC` 返回值 ≠ 3 就拒 |
| 3 | accept+0 | `cbnz r0, reject` | **分类器 `0x10163232(fp&0xff)` 必须返回 0** ← 最像"模式判别"的就是这条 |

**重要更正**：accept = `0x101765F4` 这条指令**本身就是第三个否决点**。
上一版说"跳到 accept 就是放行"是错的 —— 跳到它会先过 `cbnz r0`。
第 5b 节里 A 版只拆否决点 1，所以如果照片模式卡在否决点 3，A 会**毫无变化**。
